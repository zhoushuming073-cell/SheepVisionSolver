# v0.2 增量视觉与事务式点击

## 数据流

设计时参考了 [Screenpipe 的事件驱动截图与帧比较](https://github.com/screenpipe/screenpipe)、[ByteTrack 的目标关联](https://github.com/FoundationVision/ByteTrack)、[DXcam 的区域截图接口](https://github.com/ra1nty/DXcam)、[Cradle 的观察与行动分层](https://github.com/BAAI-Agents/Cradle) 和 [OpenAdapt 的操作验证](https://github.com/OpenAdaptAI/OpenAdapt)。仅采用思路，没有复制源代码或引入这些项目依赖。现有截图 P50 约 38 ms，故未更换为 DXcam。

首次从用户校准的 Windows 屏幕区域截图，完整识别主牌与卡槽，再创建 `VisibleMemory`。内存只保存当前可见方块、稳定 ID、`full` / `partial`、卡槽和时间戳；类型数量从方块集合派生。隐藏牌没有对象，也没有从 APK 读取实时状态。

每一步从内存决策，截图并对目标做局部类型和边框复核。鼠标事件发送后先产生 `PendingClick`，并在有限时间内检查从主牌区到卡槽的整个飞行范围。小块采样差异可发现占画面比例很小的移动牌；卡槽数量到位、连续至少 3 次安静观察、安静时间至少 120 ms，且首次变化至少经过 150 ms 后，才确认目标消失并开始局部重识别。若动画超时，直接废弃待确认操作和内存状态，等待下一次稳定画面的完整识别；绝不从运动帧重建状态。稳定画面中的类型冲突或卡槽不一致会停止下一步并尝试完整视觉同步。周边方块用位置重合度关联稳定 ID。

一次只有一个控制器工作线程和一个待确认点击。暂停、停止、Ctrl+Alt+S 通过可中断事件打断等待；GUI 主线程只接收结果、有限频率刷新预览。自动运行不保存逐步截图和调试图。手动识别仍可生成调试图。

## 实测基线与 v0.2

2026-10-27，Windows 11，当前用户保存在本地的 893×1425 游戏截图、经典模板及相同校准区。数值是本机离线回放，鼠标为模拟后端；真实窗口点击延迟及通关率不包含在内。基线使用旧版每步三次完整识别，v0.2 稳态使用同一张点击前截图和人工合成的普通单牌点击后截图。原始点击后截图出现邻牌意外变化，因此会触发安全完整同步，不适合作为普通稳态样本。基线 3 次周期、v0.2 稳态 40 次周期；样本量不同，不将二者解释为真实游戏加速倍数。

| 指标 | v0.1 基线 P50 / P95 | v0.2 初版 P50 / P95 |
|---|---:|---:|
| 区域截图 | 37.71 / 47.59 ms | 37.72 / 41.43 ms |
| 主牌与卡槽完整识别 | 5284.53 / 5313.22 ms | 5626.93 / 5910.05 ms |
| 局部识别 | 未提供 | 232.55 / 241.80 ms |
| 点击前目标复核 | 完整识别的一部分 | 4.62 / 5.65 ms |
| 点击后反馈确认 | 完整识别的一部分 | 22.63 / 32.09 ms |
| 完整周期 | 16926.12 / 18702.42 ms | 稳态 249.13 / 316.53 ms |
| 每周期完整识别 | 3 | 稳态 0；首次初始化 1 |
| 每周期截图 | 3 | 稳态 3 |

初版周期使用预载帧，所以截图调用时间接近零；上表的区域截图单独测量，不能直接视为端到端真实桌面周期。初版回放基准使用 1 ms 轮询；实际默认是 40 ms。相同批量基准的进程 CPU 占用分别是单核基准的 182% 与 96%；工作负载和样本时长不同。OpenCV 线程从默认 32 调为 1 后，当前局部匹配的单次 CPU 时间与墙钟时间均下降。初版进程 RSS 在 40 次稳态周期的第 10/20/30/40 次约为 72.0/74.8/72.1/72.2 MiB，未观察到持续增长；模板缓存上限分别为 128/64 项。

**飞行牌修复后**，同一本机私有画面、预载帧和模拟鼠标，以实际默认 40 ms 轮询及 120 ms 稳定窗口回放 20 次：点击后反馈 P50/P95 为 208.66/211.13 ms，稳态周期为 473.65/520.64 ms，每步完整识别 0 次、回放截图 6 次；单独测得真实区域截图 45.04/55.20 ms。后续截图间隔和动画长度会影响真实周期。修复前后的基准设置与样本数不同，数值仅说明安全等待的成本。20 次周期的 RSS 第 10/20 次为 71.29/71.23 MiB。

使用完全公开的程序生成图片运行 `python scripts/benchmark_synthetic.py`，在最新 150 ms 飞行牌最短观测窗口下，本机结果为：完整识别 P50/P95 130.24/134.55 ms，局部识别 35.72/43.12 ms，点击反馈 159.14/162.96 ms，稳态周期 202.25/211.49 ms。此脚本为快速回归使用 1 ms 轮询与 10 ms 安静窗口，但仍受 150 ms 最短观测限制；小型合成场景不代表真实游戏复杂度或默认运行延迟。RSS 在第 10/20/30/40 次约为 50.96/51.46/51.52/51.82 MiB。

## 回归与剩余问题

`python -m pytest -q` 本机带授权经典模板时 43 项通过，包括稳定 ID、部分到完整、新牌出现、点击事务、三消、错误恢复、互斥点击、可中断等待、飞行牌穿过其他牌、动画超时停机、卡槽余两格时受限解锁、控制窗口避让游戏区域、Windows `SendInput` 顺序和 2000 次增量合并内存约束。公开克隆环境缺少模板时，依赖原版模板的附加测试会跳过。

现场停机复盘：卡槽为 `15,15,1,1,9` 时，原策略只寻找直接三消而停止。新策略仅在余两格、已有同类牌可配对，且该候选与一张已识别的部分遮挡牌重叠、后者在卡槽已有两张时，允许尝试移开候选。尝试后必须重新观察；若目标牌仍不可点，卡槽到 6 格即停止。手动重新识别会丢弃旧控制器记忆，避免 GUI 画面与增量状态不同步。这是针对已知可见信息的轻量启发式，不保证解局。桌面单步尝试了这个 9 号牌，画面没有变化，事务正确超时停机；尚不能断定是牌本身被挡住还是模拟器没有接收点击。

另一个现场问题是求解器窗口默认位置覆盖了校准的游戏区域；此时“获取截图”会拍到程序自身。GUI 现在根据物理屏幕坐标主动移到游戏区域外；没有足够空间则拒绝截图和自动启动。自动移动后要求重新截图，避免使用移动期间的帧。

真实保存画面的原始点击后帧出现邻牌变化，安全回退到完整同步，单次回放约 12.7 秒；这条路径仍慢。完整初始化约 5.6 秒，也是当前主要瓶颈。卡槽占用检查是启发式，其他皮肤、缩放和动画需在 Windows 游戏窗口继续核验。后续 Windows/MuMu 短时实测中，`mouse_event` 改为 `SendInput` 并显式聚焦目标窗口后，完成 1 次单步及随后 11 次连续确认点击；停止后重新识别真实卡槽。两项输入改动同时进行，无法单独归因。一次局部冲突后的完整同步约耗时 8.1 秒；尚无长时间运行和独立关卡通关率结果。

## 复现

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[desktop,dev]"
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD='1'
.venv\Scripts\python -m pytest -q
$env:PYTHONPATH='src'
.venv\Scripts\python scripts\benchmark_synthetic.py
.venv\Scripts\python -m sheep_solver.gui.app
```

本地私有画面基准脚本及输入均在 `.gitignore` 排除的 `data/research/` 和 `dist/data/` 中，不随公开仓库发布。打包命令为 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_windows.ps1`；需先按 README 提取本地经典模板，APK 和素材不会提交。

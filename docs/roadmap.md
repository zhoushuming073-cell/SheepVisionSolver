# SheepVisionSolver — 开发路线与技术规范

## 一、项目目标

开发一个针对《羊了个羊》的视觉自主求解系统。

第一阶段只研究**每日挑战**，暂不支持难度更高的“羊羊大世界”。

最终要求：

1. 通过游戏截图识别牌面。
2. 理解牌的种类、位置、遮挡关系和底部卡槽状态。
3. 在不知道隐藏牌内容的情况下，自主计算下一步。
4. 自动执行点击并观察结果。
5. 重复决策，直至通关或失败。
6. 记录每次决策、搜索过程与失败原因。

**核心约束：正式 Solver 只能使用玩家通过屏幕实际能够获得的信息。**

允许通过逆向研究构建本地模拟器，但禁止正式求解模块调用游戏内部答案、隐藏牌数组、通关接口或其他作弊数据。

---

## 二、总体技术架构

采用五层设计：

```text
SheepVisionSolver
│
├── Game Research
│   ├── REA 逆向研究
│   ├── 游戏规则还原
│   ├── 图案素材整理
│   └── 本地游戏模拟器
│
├── Perception
│   ├── 截图获取
│   ├── 牌面识别
│   ├── 几何位置识别
│   ├── 遮挡关系重建
│   └── 当前局面结构化
│
├── Planning
│   ├── 贪心算法
│   ├── Beam Search
│   ├── 隐藏信息建模
│   ├── 蒙特卡洛模拟
│   └── 动态重规划
│
├── Control
│   ├── 鼠标 / ADB 点击
│   ├── 操作结果验证
│   └── 异常恢复
│
└── Evaluation
    ├── 模拟关卡测试
    ├── 真实每日挑战测试
    ├── 算法对比实验
    └── 通关率与失败分析
```

主要语言推荐 Python。

- 游戏模拟与搜索：Python。
- 图像识别：OpenCV，必要时引入目标检测模型。
- 真实设备控制：ADB 或桌面自动化。
- 本地游戏 UI：优先沿用逆向识别出的原始技术体系；若无法直接复用，选择轻量绘制方案。
- 测试：pytest。

避免为了技术栈统一而重写已经能够准确运行的游戏逻辑。

## 三、阶段 1：使用 REA 研究游戏

### 目标

使用 REA（Reverse Engineer Anything）辅助分析游戏，建立准确的规则文档和素材库。

项目地址：https://github.com/morluto/rea

### 研究任务

1. 整理所有牌面图案及其对应编号。
2. 研究牌的生成、堆叠、遮挡与可点击规则。
3. 确认三个同类牌消除的具体逻辑。
4. 确认七格卡槽的失败判定。
5. 研究主牌区、辅助牌区和盲盒区的具体机制。
6. 研究游戏道具的规则。
7. 尽可能还原每日挑战的关卡生成机制。
8. 判断隐藏牌是在开局确定，还是在点击过程中动态生成。

尤其要回答：

- 同一关卡重复开始，布局和牌面是否相同？
- 所有牌的总数量及各类型数量是否具有固定约束？
- 底牌是否存在生成规律？
- 每一关是否保证至少存在一条无道具通关路径？

### 交付物

- `docs/game_rules.md`：准确的游戏规则。
- `docs/reverse_findings.md`：逆向发现、证据和未确认问题。
- `assets/`：本地研究使用的牌面及界面素材。
- `data/rules.json`：机器可读取的规则配置。

### 验收标准

核心规则能够通过实际游戏操作复现和验证。

对于尚未确认的机制，必须标注为“假设”，不得将推测当作事实写入求解算法。

## 四、阶段 2：构建本地游戏模拟器

**这是整个项目最重要的基础工程。**

在开发复杂 AI 前，先实现一个能够完整运行的本地《羊了个羊》。

### 核心功能

1. 加载一局关卡。
2. 显示不同层级的牌。
3. 正确判断哪些牌可以点击。
4. 点击后更新所有遮挡关系。
5. 将牌加入卡槽。
6. 自动消除三个相同图案。
7. 判断胜利、失败。
8. 支持重新开始和记录操作历史。
9. 支持批量、无界面的高速模拟。

### 游戏状态表示

每张牌至少包含：

```python
Tile(
    id,
    type_id,
    x,
    y,
    width,
    height,
    layer,
    region,
    blockers,
    removed
)
```

整个局面包含：

```python
GameState(
    tiles,
    tray,
    remaining_count,
    game_status
)
```

其中 `blockers` 表示遮挡当前牌的其他牌。

对于盲盒、辅助区等特殊机制，应建立独立状态字段，不能强行当作普通叠层牌处理。

### 关键设计

必须区分两种状态：

- `FullState`：包含完整底牌信息，仅供模拟器和离线求解实验使用。
- `Observation`：只包含当前屏幕可观察到的信息，供正式视觉 Solver 使用。

二者之间必须建立严格的信息隔离。

### 验收标准

- 模拟器的合法点击判定与真实游戏一致。
- 卡槽、消除、失败、胜利规则正确。
- 可以使用固定随机种子重现关卡。
- 不依赖 UI，即可运行数千局算法实验。

## 五、阶段 3：开发完全信息求解器

这一阶段暂时不处理视觉和隐藏牌。

假设计算机知道所有牌的位置、类型及遮挡关系，研究算法本身能否解出关卡。

### 算法路线

**Baseline A：随机策略**

随机选择合法操作，建立最低性能基准。

**Baseline B：贪心策略**

优先选择能够：

- 完成三消；
- 解锁更多牌；
- 降低卡槽占用；

的操作。

**Algorithm C：Beam Search**

作为第一版主力搜索算法。

每次生成候选动作，并依据评价函数筛选最有希望的若干局面。

搜索应保留不同的牌面结构状态，而不能仅依据剩余牌数量或图案数量进行去重。

**Algorithm D：DFS / 回溯搜索**

用于较小关卡的完整搜索和正确性验证。

在算力允许的局面中，作为检验 Beam Search 是否遗漏可行解的参考。

### 评价函数

初步考虑：

```text
局面价值 =
    消除进度收益
  + 解锁新牌收益
  + 可形成三消的机会
  - 卡槽拥堵风险
  - 未来可选操作减少风险
  - 关键辅助资源消耗
```

评价函数必须支持独立调整权重。

后续通过实验确定参数，不直接假设某组权重最优。

### 验收标准

- 可以求解小型完整信息关卡。
- 与随机、贪心策略完成公平对比。
- 能输出完整解法路径。
- 能说明搜索失败是超时、资源限制还是确实无解。

注意：Beam Search 搜索失败，不等于证明关卡无解。

## 六、阶段 4：开发视觉识别系统

### 目标

仅通过截图，恢复当前可观察的游戏局面。

### 识别任务

1. 定位游戏区域。
2. 识别每张可见牌的图案。
3. 检测牌的中心坐标、边界框。
4. 判断牌是否被遮挡以及能否点击。
5. 识别底部卡槽。
6. 区分主牌区、辅助牌区和盲盒区。
7. 将无法识别的牌标记为 `unknown`。
8. 输出统一的 `Observation` 对象。

### 技术路线

优先使用已经提取出的图案素材进行模板匹配。

如果遇到遮挡、缩放、动画等问题导致识别不稳定，再考虑训练目标检测模型。

不要一开始就引入大型神经网络。

### 调试功能

提供可视化调试界面，在截图上叠加：

- 牌的编号。
- 识别出的图案类型。
- 点击坐标。
- 遮挡关系。
- 识别置信度。

### 验收标准

建立人工标注的截图测试集，统计：

- 图案识别准确率。
- 可点击状态识别准确率。
- 遮挡关系识别准确率。
- 单帧处理时间。

发现低置信度或结构矛盾时，优先重新截图，不能强行猜测。

## 七、阶段 5：开发不完全信息求解算法

这是正式 Solver 的核心研究阶段。

与阶段 3 不同，此时算法**不知道被遮挡牌的类型**。

### 核心框架

采用：

**Beam Search + 动态重规划 + 隐藏信息风险评估**

工作流程：

```text
读取当前截图
    ↓
构建 Observation
    ↓
生成合法操作
    ↓
Beam Search 评估未来局面
    ↓
评估隐藏牌风险
    ↓
选择一个动作
    ↓
实际点击
    ↓
重新观察、重新搜索
```

### 搜索优化

尝试以“一次完整三消”为搜索单元，减少搜索树深度。

但必须检查过程中是否可能导致卡槽失败，不能只判断三消完成后的状态。

### 隐藏牌处理

初期先使用保守策略：

- 不假设隐藏牌的具体图案。
- 尽量选择能够打开更多有效操作空间的动作。
- 避免积累大量难以配对的单张牌。
- 对盲盒及辅助区资源建立机会成本。

在确认发牌分布或获得可靠经验模型后，再引入蒙特卡洛模拟：

1. 根据已知信息生成多个可能的隐藏布局。
2. 分别模拟候选操作。
3. 估计后续成功概率及失败风险。
4. 选择具有较好风险收益的操作。

如果隐藏牌分布没有可靠依据，模拟结果不得宣称为真实通关概率。

### 验收标准

在同一批测试关卡上，比较：

- 贪心策略。
- 普通 Beam Search。
- 加入遮挡结构评价的 Beam Search。
- 加入隐藏信息风险评估的搜索算法。

必须通过实验判断复杂算法是否真正带来提升。

## 八、阶段 6：实现真实游戏自动控制

### 功能

1. 自动获取截图。
2. 调用视觉模块。
3. 调用规划模块。
4. 生成点击坐标。
5. 执行一次点击。
6. 等待动画结束。
7. 重新截图。
8. 确认操作是否生效。

### 异常处理

- 点击未成功：重新识别。
- 画面出现动画：等待稳定。
- 图案识别冲突：暂停决策。
- 当前局面与预测不一致：废弃旧搜索结果并重建状态。
- 游戏结束：保存完整日志。

**每次只执行已确认的一步，然后重新观察。**

避免一次性执行长点击序列，因为新暴露的牌会改变最佳决策。

## 九、阶段 7：建立算法实验系统

最终评价指标不应只是“有没有通关”。

至少记录：

| 指标 | 说明 |
|---|---|
| 通关率 | 最核心指标 |
| 无道具通关率 | 衡量算法真实求解能力 |
| 平均剩余牌数 | 失败时距离通关还有多远 |
| 平均决策耗时 | 算法计算成本 |
| 搜索节点数量 | 搜索效率 |
| 卡槽溢出次数 | 风险控制能力 |
| 视觉识别错误率 | 感知系统可靠性 |
| 操作执行错误率 | 自动化可靠性 |

### 测试分类

**A. 完全信息模拟测试**

衡量纯搜索算法。

**B. 理想视觉测试**

只提供当前可见信息，但不引入识别错误。

衡量不完全信息决策能力。

**C. 真实视觉测试**

使用真实截图与自动点击。

衡量整个系统的实际性能。

测试应固定关卡、记录随机种子，并保留未参与算法调参的独立测试集。

## 十一、开发原则

1. 采用模块化结构，确保逆向、模拟、视觉、算法能够独立开发和测试。
2. 优先保证游戏逻辑正确，不急于做精美 UI。
3. 每个阶段都必须提供可运行程序与测试。
4. 不得使用隐藏牌信息提高正式 Solver 的通关率。
5. 所有算法改动都应保留实验记录。
6. 不擅自修改已经验证正确的模块接口。
7. 优先使用简单、可解释的算法；只有在实验显示必要时才增加复杂度。
8. 任何未经证实的游戏机制，都必须明确标记为假设。
9. 原始游戏素材仅用于授权范围内的本地研究，不默认允许公开再分发。
10. 遇到依赖真实游戏数据、用户授权或关键设计选择的阻碍时，先提出问题，不编造实现细节。

## 十二、Codex 当前应该执行的任务

**现在只启动第一阶段，不要一次性实现整个项目。**

请 Codex：

1. 检查当前仓库是否已有代码，避免覆盖现有成果。
2. 初始化项目目录和基础 Python 环境。
3. 创建 `docs/roadmap.md`，保存这份开发规范。
4. 设计 `Tile`、`FullState`、`Observation` 的初始数据结构。
5. 创建游戏规则研究清单。
6. 创建 REA 逆向发现记录模板，区分事实、证据与推测。
7. 用人工构造的小型牌局开发最基础的规则引擎。
8. 编写第一批单元测试。
9. 运行测试并报告结果。
10. 列出需要用户提供的游戏文件、截图或规则证据。

暂时不要：

- 训练视觉模型。
- 开发复杂搜索算法。
- 集成真实游戏自动点击。
- 大规模复刻原游戏 UI。
- 自行假设隐藏牌生成机制。

完成后输出：

- 已创建的文件。
- 已实现的功能。
- 测试结果。
- 尚未确认的规则。
- 下一阶段建议。

等待用户确认后，再进入下一开发阶段。

## 十三、最终里程碑

- **M1：规则正确**——建立与实际机制一致的本地游戏引擎。
- **M2：算法可解**——完全信息下，能够自动解出可行关卡。
- **M3：视觉可用**——能够准确识别游戏截图。
- **M4：自动闭环**——能够看屏幕、规划、点击并重新观察。
- **M5：性能提升**——每日挑战通关率在独立测试中持续改善。
- **M6：难度迁移**——在每日挑战取得可靠成果后，研究羊羊大世界。

项目最终目标不是复刻游戏，而是研发一个能在不完全信息条件下自主决策的视觉 Solver。
